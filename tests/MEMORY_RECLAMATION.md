# Windows 发送后内存回收验证

2026-09-29，Windows x64，.NET 8，Release 构建。待发送队列仍只使用内存；以下优化不修改 JSON/HMAC/ACK 格式。

## 查到的问题与处理

- 移出队列后不会自动触发完整垃圾回收。原进程采样时托管堆约 738 MB，诊断触发回收后活对象约 5.5 MB；但进程总占用仍高。因此原数据只能证明存在大量已失效的临时对象，不能据此排除所有原生资源问题。
- `SerializeAsync` 对一个很大的字符串字段仍可能分配整个字段的缓冲。现在将字符串分块转义并写入不超过 64 KiB 的发送缓冲，Base64 的 ASCII 内容可直接填充该缓冲。
- 原来先解析 `JsonDocument` 再反序列化，且 `ReadLineAsync` / 字符串反序列化可能缓存很大的共享数组。现在读取自有 UTF-8 字节缓冲，直接反序列化一次，不产生完整的 UTF-16 网络行。
- PNG 读取优先保留原始编码；Base64 编码一次分配目标字符串，解码使用字符跨度，位图编码复用 MemoryStream 缓冲，避免额外整份副本。
- STA 剪贴板线程等待时原来没有 Dispatcher 消息循环。现在空闲与重试等待时处理消息，使 WPF/COM 资源能够完成线程相关的清理。
- 大工作完成或成功 ACK 移除队列后，合并安排空闲回收：约 2–3 秒执行一次整理，再留出约 1–2 秒进行终结资源后的第二次整理。只有估算至少 4 MiB 的工作触发；持续处理时推迟，小文本不触发。回收在后台发起，但 .NET 的全堆回收仍可能短暂暂停其他线程，不能保证所有设备上没有停顿。

## 受控测试结果

| 检查 | 结果 |
| --- | --- |
| 同一份 12 MiB ASCII 载荷序列化的额外托管分配，接收方为不保存数据的流 | 原实现约 67,154,552 字节；优化后 66,224 字节；最大单次写入 65,536 字节 |
| 生产连接代码，模拟手机 ACK，发送约 8 MiB 内存字符串后不再复制任何内容 | 载荷弱引用自动失效，未依赖测试代码调用 GC.Collect |
| 真实 STA/WIC，第一批 5 张随机 3840×2160 BGRA 图片 | 测试进程私有内存峰值约 239.3 MiB，空闲约 175.0 MiB，托管占用约 0.4 MiB |
| 同一进程第二批 5 张相同尺寸随机图片 | 空闲约 175.2 MiB，托管占用约 0.4 MiB，没有按图片数量持续累积 |
| 最后一次整理耗时 | 第一批约 2.0 ms，第二批约 1.9 ms；这是该测试机样本，不是耗时上限 |
| 接收队列中的大图片解码失败后停止服务 | 错误结果只保留字符数；停止后载荷弱引用在空闲期自动失效，不写系统剪贴板 |

WIC 测试不写入用户的系统剪贴板；它通过真实工作线程调用生产位图编码路径。进程私有内存、任务管理器的物理工作集和托管活对象是不同指标，不能互换。该测试进程也未创建完整主窗口，不能将其约 175 MiB 直接当作实际应用的固定占用。

这些检查验证了回收行为和两批图片之间的增长，不能代替数小时运行、100 MB 单图及真实手机网络/剪贴板测试。当前剪贴板图片、运行时和图像组件缓存仍可能保留内存；没有通过强行裁剪工作集来降低显示数字。

## 复现

```powershell
dotnet run --project windows/ClipBridge.MemoryChecks -c Release
dotnet run --project windows/ClipBridge.ConnectionChecks -c Release
dotnet run --project windows/ClipBridge.ClipboardMemoryChecks -c Release
```

真实使用：更新 Windows 程序，保持上一轮支持 ACK 的手机端；复制图片并确认手机收到，停止复制约 5 秒后观察。重复同尺寸图片多次，记录每次空闲后的私有内存及工作集，检查是否稳定；断线时未确认内容应仍保留，不能为了降内存丢弃待发项目。
